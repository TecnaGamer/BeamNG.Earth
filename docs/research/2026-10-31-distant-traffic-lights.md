# Distant traffic lights: source study (2026-10-31)

Study for [GitHub issue #565](https://github.com/TecnaGamer/BeamNG.Earth/issues/565): lightweight moving white/red vehicle lights on roads, tied to traffic, local time and distance. No feature implementation or game-state changes in this study. Source snapshot: `dev` at `55ddc41840395776c3f36293df30791f4ddac233`, matching the running `1.7.3-beta.dev.97` release (parent session verified upstream branch/tag and installed module hashes). The base `VERSION` file still reads `1.7.3-beta`. Relevant findings were revalidated after switching from stable main; source links below refer to this dev snapshot.

**Fact** below means verified in this source snapshot. **Proposal** and **Probe** identify design choices and work still needing runtime evidence. Existing historical engine measurements in comments are context, not measurements repeated here.

## 1. Main finding

There is no existing moving distant-traffic-light system in the inspected modules. `farcars.lua` saves and unloads the player's own cars and explicitly excludes traffic; `nightlights.lua` changes building/lamp materials and manages nearby street-lamp spotlights. Their names do not imply this feature already exists. [farcars.lua:1–15](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/farcars.lua#L1-L15), [nightlights.lua:1–44](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/nightlights.lua#L1-L44).

The client already has **some road geometry beyond the graph handed to real traffic**, but it is the un-clipped server navgraph, not a separate far-road network. Roads farther away are read on the server for far/skyline street lamps; only lamp positions reach the client. Therefore a short-range client-only experiment is possible, while a reliable multi-kilometre effect needs additional server-produced visual path data. [navgraph.lua `onMessage`, `toNodes`, `currentGraph`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L101-L173), [navgraph.lua:558](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L558), [buildings.py `far_lamps`](../../server/buildings.py#L3112-L3211).

## 2. Road data that actually exists

| Source | Available information | Reach and limitation |
|---|---|---|
| Raw server navgraph | Stable connector/segment node names; `[x,y,z,radius]`; edges `[in,out,oneway,lanes_out,lanes_in,target_speed,drivability,radius]`; country road rules | Half-square `WINDOW_M = 1100`, rebuilt after `REBUILD_M = 400` movement, asynchronously. Not a constant camera-centred 1.1 km disc. |
| Graph in stock `map` | Raw graph clipped to terrain box minus `EDGE_M = 60`; steep links rejected | Intended for physical cars. Using `map.getMap()` alone loses the farther nodes. |
| Road tile payload | Mesh references, colliders, furniture rows and optional legacy chunks | Default send distance 640 m to tile edge, drop 960 m; `chunks` is empty when a road mesh is supplied. Not a dependable far centreline source. |
| Far/skyline payload | Building shapes and `lamps`: XYZ points; geotile form groups points by road geotile | Far buildings default 1600 m; skyline 4800 m. Lamp generation reads roads here, but does not serialize paths, directions, lane counts or connectivity. |

Sources: [server/navgraph.py:27–37, `build`](../../server/navgraph.py#L27-L37), [`Tracker`](../../server/navgraph.py#L473-L534), [client `toNodes`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L101-L159), [server/roads.py:41–44](../../server/roads.py#L41-L44), [`write_tile`](../../server/roads.py#L8395-L8497), [buildings.py:2739–2741](../../server/buildings.py#L2739-L2741), [`far_items`, `far_tile`](../../server/buildings.py#L3042-L3087), [`far_lamps`, skyline constants](../../server/buildings.py#L3112-L3226), [client `onFarGeo`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/roads.lua#L1199-L1265).

**Important correction to an old comment:** `navgraph.lua` describes a roughly 450 m block, but current `lattice.lua` configures 1024 or 512 samples at 2 m spacing: collidable widths are **2046 m or 1022 m**. With the 60 m clip margin, the default block can already expose traffic graph nodes roughly 964 m from its centre. A raw 1100 m half-window adds only a narrow strip on a freshly aligned default block; after movement it can fail to extend beyond the clipped traffic area on some sides. There is no guaranteed broad distant annulus without measuring the current block and graph coverage. [lattice.lua `configure`, `groundBox`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/lattice.lua#L25-L63), [navgraph.lua:14–25](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L14-L25).

The raw navgraph is retained in `graph` before clipping and already exposed by `currentGraph()` (commented as for tests). A consumer must treat it as read-only: `transform()` replaces its node table on rebase, and new messages replace the graph. Stable names allow matching surviving paths; object identity or serial alone is insufficient because a rebase keeps the serial. [navgraph.lua `onMessage`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L163-L173), [`transform`, `currentGraph`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L537-L558).

The server navgraph already handles one-way reversal, both driving sides, mapped lane splits, curve speed targets, bridge deck elevations and Earth curvature. Tunnel spans are deliberately excluded. Its output does **not** retain an explicit road class or tunnel flag, so those cannot be read back reliably from speed/drivability. Reusing it avoids inventing straight lines across terrain, but does not guarantee all distant bridges have accurate deck heights: both server build paths catch bridge failures and fall back to ground. [navgraph.py `build`](../../server/navgraph.py#L192-L371), [earthd.py `build_navgraph`](../../server/earthd.py#L1204-L1259), [blockworker.py `navgraph`](../../server/blockworker.py#L429-L470).

**Dev-specific alignment concern:** the current dev adds `road_tapers`, `lane_shifts`, `deck_shift_fn` and per-point widths to drawn road/deck geometry. `navgraph.build` still uses the mapped polyline without those explicit shift calls. A future visual path builder should reuse the shared carriageway/shift policy, and a raw-graph experiment must inspect merge/split alignment rather than assume exact lane centring. This is a source-based concern, not a measured defect in the running scene. [roads.py `lane_shifts`, `shift_at`](../../server/roads.py#L1808-L1870), [`deck_shift_fn`, `shifted_parts`](../../server/roads.py#L7075-L7102), [`build_tile`](../../server/roads.py#L7725-L7737), [navgraph.py:202–208](../../server/navgraph.py#L202-L208).

Far lamp points cannot reconstruct this graph: `far_lamps` places them beside roads at ground + 8 m, filters by lighting rules/built-up squares, and returns rounded XYZ only. Sorting these points into a moving route would invent junctions, miss unlit roads and use the wrong height. The existing road layers and tile ownership are useful **server-side inputs** for a future path payload. [buildings.py:3091–3211](../../server/buildings.py#L3091-L3211).

## 3. Traffic and clock semantics

**Fact:** server `--traffic on` means “produce the AI graph”, not “the player currently has traffic enabled”. It defaults on and also requires roads/map data. `navgraph.choice` captures the initial freeroam choice; the radial menu can change traffic later. The existing module queries live `gameplay_traffic.getState()` for its guard and status. [earthd.py:853](../../server/earthd.py#L853), [earthd.py:6157–6160](../../server/earthd.py#L6157-L6160), [navgraph.lua `takeChoice`, `startTraffic`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L477-L532), [`status`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L695-L702).

**Proposal:** gate the effect from live traffic state and effective active amount, with “parked only” excluded. Do not equate the server flag, initial choice, graph availability or existence of parked/BeamMP cars with active traffic. **Probe:** establish live state/active-count behavior for radial-menu remove, enable, pause, vehicle pooling and teleport holds before choosing the precise gate. `onTeleport()` temporarily sets active amount to zero while retaining the traffic system; that transition should not be mistaken for a permanent player setting. [navgraph.lua `onTeleport`, `update`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L560-L685).

**Fact:** the existing sky owns real/manual time and optional BeamMP server time. TimeOfDay uses noon = 0, midnight = 0.5; the local hour conversion used by `sky.status()` is `((tod.time + 0.5) % 1) * 24`. Weather may replace the guessed UTC offset. `nightlights.isNight()` uses the engine's `core_environment.getLightState().isNight`, not a hardcoded clock interval. [sky.lua:1–18](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/sky.lua#L1-L18), [`sync`, `setServerClock`, `status`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/sky.lua#L146-L219), [nightlights.lua `isNight`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/nightlights.lua#L56-L64), [weather.lua:720](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/weather.lua#L720).

**Proposal:** density follows a smooth, documented local-hour curve (lower overnight, higher daytime/commute periods); visible intensity separately follows ambient day/night, with a daytime reduction. Read the current game clock so manual time and MP clocks behave coherently. A demographic traffic model and exact rush-hour multipliers are outside the existing data: the curve is an artistic approximation, not measured real-time traffic. Time jumps should change the target population gradually rather than respawning every point at once.

## 4. Rendering and performance boundaries

**Fact:** `nightlights` pools up to 128 default shadowless `SpotLight`s (quality: 48/128/256), selects nearby lamps every 0.25 s, and builds at most four lights per step. Building/lens emissive materials are changed on day/night transitions, checked every second. This is appropriate for light cast onto nearby surfaces; it is not a ready moving-particle renderer. [nightlights.lua:23–44](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/nightlights.lua#L23-L44), [`newLight`, `stepLights`, `update`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/nightlights.lua#L127-L216).

**Fact:** farther street lights use `lampglow` Forest shapes, not a bank of far real lights. The generated shape is an emissive sphere with progressively larger LOD meshes to remain visible at distance, using the lamp material; its group is disabled by day. This establishes an existing asset/material pattern, but no continuous per-instance alpha fade or vehicle-facing white/red behavior has been verified. [trees.lua `GROUP_MAX_M`, `NO_COLLIDE`, `groupOff`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/trees.lua#L27-L55), [trees.lua:197](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/trees.lua#L197), [nightlights.lua `apply`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/nightlights.lua#L66-L83), [build_lamp_glow.py:1–31](../../tools/build_lamp_glow.py#L1-L31).

**Proposal:** compare a bounded pool of render-only emissive shapes against a supported batched billboard/particle path in a disposable engine probe. Use normal depth testing so terrain/buildings occlude traffic, no shadow casting, no collision and no per-light surface illumination. Do not select debug drawing as production rendering without verifying occlusion, post-effects and behavior outside developer mode. Head/tail visibility should depend on path tangent versus direction to camera, with a softened side-on transition; arbitrary white/red alternation along a line would not match vehicles.

**Probe:** verify material tint/alpha control per instance, whether opacity updates are inexpensive, apparent size under bloom/exposure/FOV, move cost at the proposed cap, and depth behavior behind a hill/bridge/building. The existing lamp spheres have stepped distance LODs, so reusing them alone does not satisfy smooth fade. No FPS or object-count promise is supported by this read-only study.

**Fact:** the main frame governor targets 2 ms streaming work (1–4 ms configurable), 8 ms while loading, and isolates expensive operations with quiet frames. `navgraph` prepares tables in 2 ms coroutine slices and waits for a suitable frame before `map.reset`; its comments record costly graph applications. `core.onUpdate` gives roads priority over far terrain and skips most updates during a pending rebase. [governor.lua:1–58](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/governor.lua#L1-L58), [navgraph.lua:582–665](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/navgraph.lua#L582-L665), [core.lua:2059–2148](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/core.lua#L2059-L2148).

**Proposal:** bounded candidate/path/light counts; cached cumulative path lengths and deterministic seeds; rebuild candidates only on graph/tile changes or coarse spatial/time intervals. Advance motion by `dtSim` (freeze with physics pause) and interpolate positions smoothly; do not rebuild engine objects or scan/sort the whole graph every frame. Charge creation/deletion and route preparation to the governor, respect heavy/quiet frames, and expose status/timing counters. CPU/GPU caps and update frequency require measurement on at least a lower-end target, not values copied from the static lamp pool.

## 5. Lifecycle and integration seam

**Fact:** `core.finishRebase` moves roads/trees/nightlights and then calls `navgraph.transform(xf, anchorId)` before committing the new active anchor. A teleport separately invokes module `onTeleport` hooks; mission end explicitly resets the world modules. Road/geotile drop/replacement and far-light coverage also own cleanup. [core.lua:575–614](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/core.lua#L575-L614), [core.lua:2375–2383](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/core.lua#L2375-L2383), [core.lua:2274–2298](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/core.lua#L2274-L2298), [roads.lua `dropTile`, `onGeoTile`, `dropFarGeo`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/roads.lua#L275-L309), [roads.lua:656–715](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/roads.lua#L656-L715), [roads.lua:1185–1197](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/roads.lua#L1185-L1197).

**Proposal:** a small independent GE Lua module owns cosmetic route state, motion, renderer pool and counters; `core` supplies lifecycle calls and world state, rather than embedding another large subsystem in `core.lua`. A raw-navgraph experiment can consume `currentGraph()` without mutating it. On rebase, either transform existing light positions in the same phase or rebuild from the already transformed source before display; never transform a shared graph twice. On teleport, hide/clear old cosmetic state immediately and wait for matching destination data; the old graph can remain alive temporarily for real traffic handling. Reset must delete owned objects and drop all references. Disconnect/reconnect, server restart and content replacement require explicit stale-session handling.

For larger range, retain routes in tile-local coordinates, keyed by content/version and stable feature ID, and place them into the active anchor using existing geotile arithmetic. `geotile.placement/apply` includes the height-dependent shear; XY translation alone is insufficient. Ownership must prevent duplicate lights where adjacent tiles share a road. Existing `roads.onGeoTile` hash reuse and far-geotile orphan/drop behavior are useful precedents, not automatic lifecycle coverage for new data. [geotile.lua:1–8](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/geotile.lua#L1-L8), [`placement`, `apply`, `frameOf`](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/geotile.lua#L109-L157), [roads.lua:657–715](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/roads.lua#L657-L715), [roads.lua:1147–1265](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/roads.lua#L1147-L1265).

**Proposal for distance fade:** derive the inner exclusion from actual real-traffic coverage/ground box and camera relationship, not a guessed fixed radius; multiply smooth inner and outer fades, plus fading at incomplete path boundaries/data replacement. Avoid cosmetic and physical cars displaying in the same area. This is an illusion of unrelated distant traffic, not a seamless conversion of each dot into a real vehicle. A broad overlap-free range is a product decision still requiring a probe of actual traffic spawn visibility, including free camera and highway speed.

## 6. Options before implementation

| Option | Server change | Assessment |
|---|---|---|
| A. Existing raw navgraph | None | Smallest feasibility experiment. Reuses topology, direction and Z, but the default terrain/graph sizes leave little assured distant-only space; graph boundaries move, and far Z can be approximate. Do not present it as a multi-km solution. |
| B. Optional visual path payload in existing far/geotile streams | Yes | Preferred candidate for a broad effect. Reuse roads already loaded for far lamp generation; serialize simplified paths, stable IDs, direction/lane offset guidance, speed/class, usable Z and tunnel/bridge policy. Keep it independent of buildings being enabled, with bounded range/work and capability negotiation. Existing far lamps depend on buildings and lit-area heuristics; traffic paths must not inherit those filters. |
| C. Dedicated visual-road tile stream | Yes | More explicit ownership, selective major-road coverage and independent refresh/range; adds protocol/cache/tracker work. Worth considering if B would make building payload/lifecycle ownership unclear. |
| D. Increase `WINDOW_M` and keep applying the enlarged graph to stock traffic | Yes | Poor separation. Enlarges demand fetching, bridge/elevation work and main-thread graph preparation for a cosmetic effect. It does not remove the required physics clip. The current worker already limits far grading to planned cells to avoid costly planning. |

Evidence informing these tradeoffs: [far lamp inputs/filtering](../../server/buildings.py#L3112-L3211), [server navgraph scheduling/gating](../../server/earthd.py#L4848-L4867), [worker graph cost and elevation policy](../../server/blockworker.py#L429-L470), [existing far protocol capability setup](../../server/earthd.py#L4180-L4195). **Inference:** B/C can use existing map sources without a new external data provider, but neither payload nor its road-height policy already exists. Attaching a payload must not force expensive full near-road grading/meshing at skyline range. Correct far bridge/tunnel placement is the main server-side unknown.

## 7. Validation plan and project conventions

Existing examples: pure Lua helpers with `T.check` and engine stubs; Python `unittest` fixtures. `test_navgraph.lua` covers clipping, one-way lanes and coroutine preparation; `test_nightlights.lua` covers lens ownership, nearest selection, rebase/drop and day/night; `test_core_stubbed.lua` exercises session/rebase/restart logic but explicitly does not prove engine rendering. Server graph tests include curvature, tunnel exclusion and bridge Z. These are suitable extension points after choosing a design, not proof of this unimplemented effect. [test_navgraph.lua](../../mod/tests/test_navgraph.lua#L1-L62), [test_nightlights.lua](../../mod/tests/test_nightlights.lua#L1-L30), [test_core_stubbed.lua:1–7](../../mod/tests/test_core_stubbed.lua#L1-L7), [test_navgraph.py:54–120](../../server/tests/test_navgraph.py#L54-L120).

Meaningful future tests: deterministic sampling and bounded counts independent of graph/table iteration order; allowed one-way/left-hand lanes; arc-length motion across bends without teleporting at segment boundaries; smooth fade endpoints; manual/real/MP clock and midnight continuity; traffic-off/parked-only gating; stale anchor/session rejection; no pool leaks after teleport/reset; rebase preserves geodetic route positions; duplicated tile borders and replacement continuity. If adding a payload, test geometry/schema/height ownership and old-client compatibility. A renderer integration test must verify that no collision rebuilds or traffic vehicle spawns are introduced by the effect.

Runtime probes still required before committing to a renderer/range:

1. Measure raw graph coverage versus applied traffic graph and visible physical-car range in default/small block modes, at highway speed and with free camera.
2. Benchmark emissive object/billboard choices at a bounded cap; inspect occlusion, side-on color, bloom, daylight reduction and smooth near/far fade with fixed-camera screenshots.
3. Inspect curved roads, one-way divided motorways, left-hand traffic, hilly roads, viaducts and tunnel portals; verify dots stay on the rendered carriageway and at vehicle-light height.
4. Exercise radial-menu traffic changes, parked-only, paused/slow simulation, manual clock jumps, server clock, teleport/rebase/reconnect and mission exit; verify no lingering objects or stale lights.
5. Compare frame-time percentiles and CPU/GPU/object counts with the effect off/on while streaming a dense city and a highway; inspect governor timing. No benchmark was run for this note.

Style to follow: the nearby modules use `local M = {}` / `return M`, two-space indentation, single-quoted Lua strings, unit-bearing `M.UPPER` constants exposed to tests, small pure helpers around engine adapters, and `update/status/reset/transform` lifecycle functions. English comments explain purpose, units and observed constraints, often naming the originating issue or research. Match that local style without a new helper framework. `core.lua` already notes Lua's 200-local chunk limit; keep new subsystem state out of that chunk. [nightlights.lua](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/nightlights.lua#L6-L64), [core.lua:2609](../../mod/beamng_earth/lua/ge/extensions/beamngEarth/core.lua#L2609).

The documented runners are Python `unittest` and plain LuaJIT test files. The release workflow builds native kernels and packages/smoke-checks the application; it does not establish that the full behavioral suite passed. If reusing new geometry kernels, dev's `earthfast` minimum is **120**, with removed Python twins: do not base a design on an obsolete Python fallback. [README.md:291–292](../../README.md#L291-L292), [release.yml](../../.github/workflows/release.yml), [fast.py:1–28](../../server/fast.py#L1-L28).
